# Account deletion and App Review

Deploy the backend before distributing the iOS build. No database migration or
email service is required.

## Customer flow

- Web: Account settings (cog) → Danger zone → Permanently delete account.
- iOS: Settings → Danger zone → Permanently delete account.
- Read the consequences, enter the signed-in account's email, and confirm.
- Successful deletion signs out and displays “Account deleted”.
- A wrong email or failed request leaves the account intact. The native form
  keeps the email and displays the request error.
- The web confirmation uses a native server-rendered form and works without
  JavaScript, CSS or icon fonts. German and English copy are supported.

Confirmation currently proves intent, not control of the email inbox. A future
email-verification step must be added before invoking the shared deletion service;
do not send confirmation emails or require support contact in this implementation.

## Data policy

Deletion is permanent in the live application database. It removes the user,
passkeys, sessions, associated enrollment links and authentication flows.
Memberships are removed. Kitchens with no remaining members/references are
deleted with recipes, ingredients, steps, unused tags, meal plans and copy links.
Kitchens with other members remain available to them; a retained personal
kitchen gets the neutral name “Shared kitchen”. Existing independent recipe
copies on other servers are not linked to the account and cannot be recalled.

Normal operator backups follow the operator's retention policy. Restoring an old
backup must not silently restore deleted accounts; operators must handle deletion
requests when restoring data. This feature does not alter backup retention.

## Physical-device recording for Apple

Use a disposable account, not a real customer or the reusable review account.

1. Install the submitted build on a physical iPhone and start iOS screen recording.
2. Show account creation or sign-in, then open Settings.
3. Scroll to Danger zone and tap Permanently delete account.
4. Show the explanation and type that disposable account's email.
5. Confirm, show Account deleted, and dismiss to the signed-out screen.
6. Stop recording and attach the recording to the App Review response.

A simulator recording does not satisfy Apple's specific physical-device request.
No physical-device recording is generated by CI. Do not claim one exists.

## Release validation

CI now also creates an unsigned Release archive for generic iOS devices and
verifies the app, share extension and widget executable/version metadata. This
catches device-only compile and archive failures independently of simulator tests.
Apple signing, provisioning and upload still run locally with the configured
Xcode account; CI's unsigned archive is not a distributable TestFlight build.

Local simulator tests use a disposable device by default (only that generated
device is removed afterwards). Set SIMULATOR_ID only when deliberately using an
existing device. Boot readiness has a three-minute limit and the Xcode test
command has a fifteen-minute limit; failures are not retried.

The background uploader reports its stage: tests, archive, upload or uploaded.
Exit 65 alone does not identify the stage. Inspect the stage and build log before
assuming Apple rejected an archive.
